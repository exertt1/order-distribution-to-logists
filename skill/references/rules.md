# Справочник правил распределения

Файл для справки: содержит правила в явном виде, чтобы их можно было
согласовать с заказчиком. Код реализует именно эти правила
(`scripts/logic_engine.py`, `scripts/utils.py`).

## 1. Группы логистов

| Условие | Группа |
|---|---|
| способ доставки `air` | авиаперевозки |
| не `air`, страна отправления Китай или Гонконг | ВЭД |
| не `air`, страна отправления не Китай | мультимодальные перевозки |
| способ доставки не указан | группа не определена → «Требует внимания» |
| не `air`, страна не указана | группа не определена → «Требует внимания» |

Признаки Китая и Гонконга: `Китай`, `China`, `CN`, `Гонконг`, `Hong Kong`,
`HK`, `Hongkong`. Сравнение без учёта регистра и лишних пробелов.

Заказ никогда не передаётся в другую группу, если в своей группе нет
доступных логистов.

## 2. Кто может получить заказ

Сотрудник доступен, если одновременно:

1. в должности есть слово «специалист» — это исключает ассистентов
   и руководителей группы;
2. текущее состояние ровно «Работает» — отпуск (в том числе по уходу
   за ребёнком), больничный и увольнение исключают сотрудника.

Группа сотрудника определяется по должности:
`авиа`/`air` → авиаперевозки, `вэд`/`вед`/`экспорт`/`import` → ВЭД,
`мульти` → мультимодальные перевозки.

## 3. Выбор логиста

Порядок приоритетов:

1. **Предпочтительный по истории** — доступный специалист группы, у которого
   больше всего заказов этого поставщика в Cloud (считаются все статусы).
2. Если предпочтительный логист недоступен или поставщик новый —
   **наименее загруженный** доступный специалист группы по числу заказов
   со статусом «в работе».
3. Ничья разрешается порядком сотрудников в выгрузке 1С (первый в списке).
4. **Один поставщик в пачке — один логист**: все новые ФУЛ одного поставщика
   в одной группе получают одно решение; для второго и следующих ФУЛ
   основание — «один поставщик — один логист».

Нормализация поставщика: нижний регистр, знаки препинания → пробел,
многократные пробелы сжимаются. `Nike Inc.` = `NIKE INC` = `nike-inc`.

Сопоставление логистов Cloud со справочником 1С: по фамилии и инициалам,
поэтому `Иванов И.И.` и `Иванов Иван Иванович` считаются одним человеком.

## 4. Повторные отправки

| Случай | Признак | Что делает навык |
|---|---|---|
| Заказ уже есть в Cloud | номер заказа совпал (без регистра и пробелов) | строка не создаётся; комментарий `Повторная отправка ФУЛа, ДД.ММ.ГГГГ` |
| Повтор внутри пачки | тот же номер встретился в пачке раньше | то же: строка не создаётся, комментарий с датой ФУЛ |

Дата в комментарии — дата ФУЛ. Если дату разобрать не удалось, пишется
«не определено», а не сегодняшняя дата.

## 5. Возможные пропуски

ФУЛ, которого нет в Cloud, хотя дата ФУЛ раньше последней даты движения
заказа в Cloud. Последняя дата считается как максимум по датам: получение УЛ,
дата подтверждения, дата получения документов. `cut-off` не учитывается —
это будущая контрольная дата, а не дата записи.

Такой ФУЛ попадает и в новые строки Cloud, и в лист «Возможные пропуски»:
решение, вносить ли заказ, принимает сотрудник.

## 6. Требует внимания

Строка попадает в список, если:

- в комментарии ФУЛ нет номера заказа;
- не указан способ доставки;
- не указана страна при не-авиа способе доставки;
- в группе нет доступных логистов (логист остаётся «не определено»).

## 7. Принятые допущения

- Ничьи по истории и по загрузке разрешаются порядком в выгрузке 1С.
- ФУЛ без номера заказа не может быть проверен на дубль, поэтому всегда
  идёт в «Требует внимания», даже если похожий заказ уже есть в Cloud.
- Дублирующий ФУЛ не получает нового логиста: предполагается, что заказ
  уже ведёт назначенный ранее логист.
- Один поставщик в разных группах (например `air` и `sea`) распределяется
  независимо: пачка = поставщик + группа.
- `cut-off` и дата ФУЛ переносятся без изменения значения; в ячейке
  используется формат ДД.ММ.ГГГГ.
- Неизвестные значения способа доставки (например `courier`) трактуются
  как «не air».
