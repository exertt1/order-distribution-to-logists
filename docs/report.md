# AI-агент распределения заказов между логистами

Тестовое задание: навык для GigaCowork, который распределяет новые ФУЛ между
логистами и готовит строки реестра Cloud строго по его форме.

## 1. Состав сдачи

| Что | Где |
|---|---|
| Навык (папка: `SKILL.md`, `scripts/`, `references/`) | `skill/` → архив `dist/agent.zip` |
| Системный промпт | `skill/system_prompt.txt` |
| Справочники правил и шаблон формы реестра | `skill/references/rules.md`, `skill/references/cloud_template.xlsx` |
| Тестовые данные: три файла Excel, эталон, генератор | `data/` → архив `dist/data.zip` |
| Скрипт контрольных прогонов и метрики | `tests/run_metrics.py`, `tests/metrics_report.md` |
| Сборка архивов | `build.py` |

Установка и запуск:

```bash
python data/generate.py     # пересоздать тестовые данные и эталон
python build.py             # собрать dist/agent.zip и dist/data.zip
python tests/run_metrics.py # три прогона и метрики против эталона
```

Запуск навыка (как его вызовет агент):

```bash
python scripts/main.py "<ФУЛ.xlsx>" "<Cloud.xlsx>" "<Сотрудники.xlsx>" "<папка результата>"
```

Зависимости: Python 3, `openpyxl` (для `.xls` — дополнительно `xlrd`).
Сеть, API и коннекторы не используются: навык работает только с приложенными
файлами и пишет один xlsx.

## 2. Инструмент и модель

- Инструмент проверки: Chatbox (десктоп) + локальный запуск скрипта навыка.
- Модель: DeepSeek V4 Pro (агентная обвязка), решения о группе и логисте
  принимает детерминированный скрипт на Python — модель только запускает
  скрипт и пересказывает результат.
- Все прогоны выполнены на синтетических данных из `data/`.

## 3. Вопросы заказчику

| № | Вопрос | Кому | Зачем спрашиваем | Допущение до ответа |
|---|---|---|---|---|
| 1 | «Чаще всех работает с поставщиком» — считать по всем заказам в истории Cloud или только по «в работе», за какой период? | Руководитель логистики | От этого зависит, кто считается предпочтительным | Считаем все заказы поставщика в Cloud, без ограничения периода |
| 2 | Если у поставщика в пачке заказы в разных группах (например `air` и `sea`) — это одна пачка с одним логистом или две? | Руководитель логистики | Правило «один поставщик — один логист» может конфликтовать с правилом групп | Пачка = поставщик + группа; группы распределяются независимо |
| 3 | Ничья по истории или по текущей загрузке — как решать? | Заказчику | Иначе результат зависит от случайного порядка | Брать первого по порядку в выгрузке 1С |
| 4 | Повторная отправка: какую дату писать в «Повторная отправка ФУЛа, [дата]» — ФУЛ, получения или обработки? | Сотрудник распределения | Комментарий уходит в Cloud, дата должна быть однозначной | Дата ФУЛ из выгрузки |
| 5 | Повторный ФУЛ пришёл, а заказ в Cloud уже `confirm` или ведётся другим логистом — менять статус/логиста? | Сотрудник распределения | Иначе можно сломать существующую запись | Ничего не меняем, только комментарий |
| 6 | ФУЛ без номера заказа — это новый заказ или брак данных? | Сотрудник распределения | Определяет, создавать ли строку Cloud | В Cloud не переносим, отдаём в «Требует внимания» |
| 7 | «Возможные пропуски»: сравнивать по дате ФУЛ или по дате получения УЛ, и что считать «последней записью в Cloud»? | Заказчику | Неверная граница даёт ложные пропуски | Дата ФУЛ против максимума дат Cloud (УЛ, подтверждение, документы); cut-off не учитываем |
| 8 | Заказ без страны при способе `air` — в авиа или в «Требует внимания»? | Руководитель логистики | Для авиа страна не влияет на группу | Отправляем в авиа, страну пишем «не определено» |
| 9 | Неизвестный способ доставки (`courier` и т.п.) — новая группа или «не air»? | Заказчику | В правилах перечислены только пять способов | Трактуем как «не air» и распределяем по стране |

## 4. Алгоритм

Псевдокод (полностью реализован в `skill/scripts/logic_engine.py`):

```
прочитать три файла (колонки — по заголовкам)
cloud_ids = номера заказов из Cloud (нормализованные)
last_cloud_date = max(даты УЛ, подтверждения, документов в Cloud)

для каждого ФУЛ:
    order_id = номер заказа из «Комментарий» (шаблон S\d+)
    supplier_key = нормализованный поставщик
    group = группа(способ доставки, страна)

    если order_id в cloud_ids:      → повтор (есть в Cloud)
    иначе если уже видели order_id: → повтор внутри пачки
    повторы: строка Cloud не создаётся,
             комментарий = «Повторная отправка ФУЛа, <дата ФУЛ>»

    пропуск = заказ не в Cloud и дата ФУЛ < last_cloud_date

    если нет номера заказа / нет способа доставки /
       (не air и нет страны)         → «Требует внимания»

пачки = группировка кандидатов по (поставщик, группа)
для каждой пачки:
    staff     = сотрудники группы
    available = staff, где должность «специалист» и состояние «Работает»
    если available пусто → логист «не определено», строка в «Требует внимания»
    иначе:
        top = у кого больше заказов этого поставщика в Cloud
        если top доступен → логист = top, основание «предпочтительный по истории»
        иначе → логист = доступный с минимумом заказов «в работе»
                основание «наименее загруженный»
        остальным ФУЛ пачки → тот же логист, основание «один поставщик — один логист»
```

Таблица решений по особым случаям:

| Случай | Решение |
|---|---|
| Повторная отправка (заказ есть в Cloud) | строки нет, комментарий с датой ФУЛ |
| Повтор внутри пачки | то же; первая строка считается новой |
| Новый поставщик | наименее загруженный доступный специалист группы |
| Предпочтительный логист в отпуске/уволен | переход к наименее загруженному, в журнале указывается причина |
| Все сотрудники группы недоступны | логист «не определено», строка в «Требует внимания», в другую группу не передаём |
| Нет номера заказа | «Требует внимания», строка Cloud не создаётся |
| Нет способа доставки / страны при не-air | группа «не определено», «Требует внимания» |
| ФУЛ раньше последней записи Cloud | новая строка + отметка в «Возможные пропуски» |

## 6. Результаты прогонов и метрики

Три прогона на одном наборе (`python tests/run_metrics.py`):

| Метрика | Значение |
|---|---|
| Полное совпадение с эталоном по всем полям | 20 из 20 ФУЛ — 100% |
| Точность по полю «заказ» | 100% |
| Точность по полю «группа» | 100% |
| Точность по полю «логист» | 100% |
| Точность по полю «категория» | 100% |
| Точность по полю «комментарий повтора» | 100% |
| Точность по полю «возможный пропуск» | 100% |
| Подставлено значений там, где данных не было | 0 |
| Воспроизводимость трёх прогонов | совпадает полностью |
| Время обработки пачки 20 ФУЛ | ≈ 0,001 с (лимит ТЗ — 1 минута) |
| Сводка | 13 новых строк, 2 повтора, 1 возможный пропуск, 5 требуют внимания |
| Устойчивость к «чужим» файлам (`tests/run_robustness.py`) | обратный порядок колонок + лишняя колонка + лист «Лист1» — результат совпадает полностью |

Пороговые значения ТЗ: точность распределения ≥ 95% (получено 100%),
форма Cloud 12 колонок без старых ФУЛ и дублей — 100% прогонов,
0 выдуманных значений (получено 0), три прогона дают одинаковый результат.

Механика проверки: `tests/run_metrics.py` читает эталон, запускает навык
трижды, сравнивает шесть полей по каждому ФУЛ, считает inventions
(«не определено» в эталоне против значения в результате) и сохраняет отчёт
в `tests/metrics_report.md`.

## 8. Что доработал бы дальше

1. Ловушка «вся группа недоступна» есть только в ВЭД; хотелось бы второй набор
   данных, где недоступна авиагруппа, чтобы проверить все ветки правил.
2. Ничьи разрешаются порядком строк — при росте данных стоит перейти
   на круговую ротацию по числу распределённых за день заказов.
3. «Возможные пропуски» сейчас информационные: строки попадают и в новые
   строки Cloud. Нужен ответ заказчика, нужно ли их исключать из переноса.
4. Поддержка `.xls` через `xlrd` реализована, но не покрыта тестами.
5. Для реальных данных нужен эталон от сотрудника распределения: наша
   синтетика проверяет правила, но не валидирует их бизнес-корректность.
6. Метрика «время сотрудника на пачку» требует замера на пилоте.
